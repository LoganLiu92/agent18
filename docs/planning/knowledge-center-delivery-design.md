# 知识中心页面、接口与交付方案

状态：M1 实施设计，尚未实现的接口均为建议合同。任务编号对应 [M1 开发包](m1-work-packages.md)，数据约束以[领域合同](../architecture/product-contracts.md)为准。实现时先补 OpenAPI/类型定义，再固定最终路径。

## 1. 首次使用与日常使用

首次使用路径：部署向导创建管理员 → 登录 `/admin` → 选择项目 → 接入一个来源 → 查看扫描结果 → 确认业务域与主题 → 补充业务说明 → 生成分层草稿 → 编辑审核 → 发布 → 用真实问题验证。

日常首页显示下一项需要处理的工作：待审核、失败任务、来源变化、缺失文档。已完成引导的用户直接进入知识总览；进度由服务端对象决定，刷新或换设备不会重新开始。

以下是页面职责设计，不是承诺所有页面必须独立路由。首版可用同一页面的标签和侧栏组合，避免导航过多。

| 页面/区域 | 用户做什么 | 关键内容与状态 | 开发包 |
| --- | --- | --- | --- |
| 项目首页 | 选择项目、继续未完成步骤 | 项目权限、已连接来源、已确认主题、待办；无权限有说明 | A02/K01 |
| 知识总览 | 判断哪些业务域已具备可用知识 | 按业务域列主题、必要文档、已发布、缺口、待审；数量可点开核对 | K03 |
| 来源列表与连接向导 | 新增 Git/允许目录/业务文本来源 | 来源种类、只读凭据引用、范围、受众；连接测试失败保留已填非敏感字段 | K02 |
| 扫描任务详情 | 查看扫描进度、失败、取消和重试 | 固定输入版本、已读/跳过清单、原因、预算、阶段；刷新继续查看 | K02 |
| 产品范围与知识地图 | 确认候选业务域、调整主题 | 左侧领域/主题，右侧关联来源和依据；合并、排除、手工新增 | K03 |
| 主题详情 | 阅读全部相关知识并补充资料 | 证据、人工规则、分层文档、缺口、适用版本；显示推断与已确认的区别 | K03/K04 |
| 生成配置与结果 | 选择主题、层次、受众并生成 | 文件/调用预算、数据出站范围、进度、成功与失败条目；允许局部重试 | K04 |
| 文档编辑与差异 | 补写、修订并核对依据 | 正文、证据侧栏、历史版本、人工修改差异；保存冲突可比较后重试 | K04/K05 |
| 审核队列与发布 | 审核特定修订、发布选定集合 | 退回原因、受众检查、质量结果、发布版本；失败保留现行版本 | K05 |
| 阅读与问答验证 | 检查客户最终能看到什么 | 受众/范围选择、答案及公开引用、不可回答原因、候选与已发布比较 | K06 |

五类文档为产品与领域、用户指南、API、工程、运维；同一主题不强制生成五篇。管理员确认适用类型，例如纯操作主题可能只需要用户指南和排障文档。业务层次、受众和发布状态分别筛选。

## 2. 自带账号的权限方案

账号属于 Agent18 部署；组织/项目成员关系决定工作范围。首版由管理员创建工作人员，无公开注册；同一个工作人员可在不同项目具有不同角色。项目配置仍沿用现有部署配置，新增项目管理界面另立任务。

| 角色 | 首版职责 | 不自动获得的能力 |
| --- | --- | --- |
| 部署管理员 | 管账号、项目成员、来源配置与维护设置 | 宿主客户业务写入身份 |
| viewer | 阅读获准项目知识 | 编辑、审核发布、读取未授权工程证据 |
| knowledge_editor | 管理知识主题、补充资料、生成和编辑草稿、提交审核 | 审核发布 |
| knowledge_publisher | 查看审核所需资料、审核/退回、发布/撤下/回滚 | 配置部署凭据、执行客户业务动作 |
| support | 处理获准客户工单、公开回复、记录内部处理信息 | 源码/原始运行证据、知识发布 |
| engineer | 调查获准工单、读取相应工程证据、提出处理建议 | 客户业务执行、知识发布 |

角色是权限组合，服务端以具体 permission 校验。建议首先固定 `knowledge.read/edit/review/publish`、`source.configure/read`、`evidence.internal.read`、`ticket.read/reply/assign`；范围由可信成员关系计算。敏感证据授权不能仅由“同项目”推导。

M1 先做项目范围的知识角色；M2 开放员工工单前补明确的允许租户范围。空范围表示无权，不能默认全部租户；需要全项目权限时显式授予。管理员可持有多种能力，但每次审阅和发布仍记录实际身份及修订。

首版允许同一个具有编辑、审核和发布权限的人完成闭环；是否要求另一人复核作为项目策略。这样单人自托管能正常使用，多人团队也能强制职责分离。

## 3. 建议的 API 分组

新增后台知识 API 位于 `/operator/projects/:projectKey/knowledge` 下，使用独立员工会话。下表省略这个前缀；不是当前已可调用接口。

| 操作 | 建议接口 | 返回或保证 |
| --- | --- | --- |
| 总览 | `GET /overview` | 真实计数、待办、范围和计数口径 |
| 来源管理 | `GET/POST /sources`、`PATCH /sources/:id` | 配置版本；响应不含密钥原文 |
| 测试连接 | `POST /sources/:id/test` | 有限范围只读检查及可操作错误 |
| 发起扫描 | `POST /sources/:id/scans` | 202 + taskId；输入 ref 解析成固定快照 |
| 任务查看/取消 | `GET /tasks/:id`、`POST /tasks/:id/cancel` | 阶段、预算、失败原因、可重试状态 |
| 范围与地图 | `GET /topics`、`POST /topics`、`PATCH /topics/:id` | 稳定主题 ID、版本；自动候选须人工确认 |
| 补充资料 | `POST /topics/:id/evidence` | 文本/已有来源关联，保留人工确认人和时间 |
| 生成草稿 | `POST /generations` | topicIds、层次、受众、快照和预算 → taskId |
| 编辑修订 | `POST /documents/:id/revisions` | baseRevision + 内容 → 新不可变 revision |
| 提交与决定 | `POST /revisions/:id/submit`、`POST /revisions/:id/reviews` | 决定绑定精确修订；退回必须有原因 |
| 发布 | `POST /publications` | revisionIds + expectedPublication + 幂等键 → 发布记录 |
| 撤下/回滚 | `POST /publications/:id/withdraw`、`POST /publications/:id/rollback` | 新事件和审计；回滚重新校验当前来源授权 |
| 评测 | `POST /evaluations`、`GET /evaluations/:id` | 固定样本/候选集/权限范围；不切换客户发布 |

列表使用稳定排序和游标分页。可重试写入带幂等键，相同键不同参数返回冲突；编辑和发布另带预期版本。错误区分输入错误、无权限、对象不可见、版本冲突、预算不足和依赖暂不可用；不可见对象的错误不能泄露跨项目标题。

客户知识继续通过现有 KnowledgeProvider 和客户 API 读取有效发布；后台评测使用单独候选读取路径。不能把内部评测的参数开关暴露给客户以读取草稿。

## 4. 扫描与生成任务方案

任务记录 project、发起人、任务种类、固定输入、预算、状态、租约、尝试次数、进度和输出引用。阶段划分为读取 → 解析 → 主题建议 → 生成；扫描成功并不代表后续生成成功。数据库记录为真源，页面轮询先行，首版不必引入另一套实时通信框架。

执行器领取时、读取新来源前以及发布结果时重新校验权限与来源状态。租约失效后允许恢复；外部模型请求结果不确定时先查任务记录，避免盲目重复调用。每阶段按输入快照和配置生成幂等输出，重试不能覆盖人工修订。

用户可以取消未执行的后续调用；正在执行且无法取消的调用完成后，其结果标记为未采纳，不自动发布。记录实际调用成本与失败原因，不承诺取消瞬间一定停止计费。

源码与业务文档属于待分析数据，内含的提示语不能修改工具权限、出站范围或发布决定。读取前排除密钥/构建产物等敏感或无关目录，按来源和模型配置决定哪些资料允许出站。

## 5. 迁移分三个交付切片

1. **新增与映射（K01）**：新增模型和旧 ID 映射，隔离库回填演练；旧发布仍可用。记录无法回填的字段为 unknown。
2. **新写入与验证（K02—K06）**：新流程写新模型；既有构建流程按明确适配规则保留。客户读取以明确发布渠道选择旧或新数据，同一文档不重复召回。
3. **按项目切换（K07）**：项目通过评测后切换；保存切换前版本与备份。回退先停止新写入，再按验证过的版本/恢复流程处理，不能简单假设删除新表即可回退。

每一片都核对旧文章引用、历史 Case、客户问答和活动发布。新后台可逐步上线，但未完成闭环的入口应说明状态，不显示伪造统计或可点击的空操作。

## 6. 每包固定交付记录

后续开发记录采用以下字段，便于逐步开展和交接：

```text
任务：Kxx / Axx / Sxx
需求与依赖：对应开发包，列出前置结果
用户流程：入口 → 操作 → 成功结果
实现：页面 / API / 存储 / 角色与范围
兼容：旧数据、旧客户端、迁移与回退
验证：成功 / 拒绝 / 未知 / 失败恢复
证据：命令结果、数据回读、浏览器验收、样本版本
限制：未实现、未接入、未部署分别说明
下一步：下一个任务编号及其可开始条件
```

一个任务完成应同时具备可操作流程和后端事实；截图不能代替权限/持久化测试，构建成功不能代替浏览器验收，合成数据不能代替实际业务确认。
