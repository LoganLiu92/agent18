**产品方向**

Agent18 为已有 SaaS 提供知识、支持、运行排查和业务洞察能力。知识中心持续整理产品知识；客户通过对话使用业务能力和报告问题；工单承载持续处理；Operations 提供运行证据；Insights 逐步扩展经营与网站分析。

产品主线固定为 Understand（知识中心）、Support（对话与工单）、Investigate（运行证据与调查）、Empower（洞察与受控行动），共用 Identity、Context、Tool、Policy、Evidence、Run、Audit。复用当前 Query、Action、Case 和知识构建实现。

Case 是内部工作对象，SUPPORT_TICKET 类型在界面显示为“工单”；其他 Case 类型有自己的来源、状态与可见性。Conversation 独立建模，通过显式 Case Link 关联，对话、工作事项和排查任务有各自生命周期。

身份方案按用户决定：Agent18 自带独立管理员和工作人员账号体系；宿主网站客户继续使用宿主身份。首轮不依赖任何外部员工登录、OIDC 或 SSO；这些只作为可选扩展。

第一批导航为“首页、知识中心、支持（对话/工单）、运行排查、接入与设置”。操作提案和历史从相关对话/工单可达；权限与审计放入设置。功能完成后再增加 Insights、独立审批或其他导航，不预置大量无法工作的空页面。

**对外部建议的取舍**

- 采纳分层知识、代码证据、知识更新提醒、完整工单页面、持久对话和受控 Insights。
- 将独立 Operator 账号与权限提前到远程知识审核和工单工作台之前，不延后到所谓 1.0；不把外部 SSO 当作前置条件。
- namespace 修复是第一项前置工作；当前证据指向线索误关联，不将其直接定性为已证实的权限绕过。
- 不按“生成文档数量”承诺完整理解代码。展示已扫描范围、解析支持、跳过项、推断和未知；接口/实体/状态机统计必须有可检查依据。
- 首轮复用 Git/目录来源；业务文档先支持文本导入与手工编辑。网站抓取、PDF、第三方文档平台分批接入，不把连接器图标当成实现。
- 检索器升级依据真实问答评测决定，不预先绑定向量数据库或某个产品。Insights 首条只读链路不依赖完整 Trace、所有连接器或代码修复。
- 里程碑依据出口验收确定版本；不将多个大型能力机械打包为 0.9，也不把版本号当作成熟度证据。

这些要求进入既有开发包，不另外建立一套并行路线图。新增或细化的共同约束如下：

- **上下文组件**：统一显示项目、环境、租户、用户、完整实体身份及 Trace；缺失值标记未知，浏览器提供的线索标记未验证。环境选择必须落到服务端授权、查询范围、缓存键和证据记录，不能只改变页面标题。知识按明确的版本/适用范围过滤，不能简单把整个知识库强制复制到各环境。
- **证据组件**：显示来源、观察时间、范围、来源版本与部署版本，按观察事实、推导、假设、已核实、人工确认区分。串联请求、日志、部署、源码时只展示确有证据的关联；缺少某一环则显示缺失，不补造链接或置信百分比。
- **知识地图组件**：围绕已确认业务域和主题展示所需文档层次、来源、受众、发布状态和缺口。覆盖率仅计算已确认范围内的明确要求，显示分子/分母及不适用项；无法识别不等于不存在。
- **角色工作入口**：客服优先工单和对话，知识人员优先草稿/审核/缺口，工程人员优先调查，管理员优先接入/账号/策略。共用导航按权限显示，深链接及所有接口独立校验；不靠隐藏菜单实现授权。
- **工单交互**：桌面可采用沟通、调查、上下文三栏，窄屏切换分区。公开回复和内部备注使用明确分离的编辑状态、存储字段与接口投影；发送前显示实际接收范围。客户摘要不能直接复制内部日志和源码。
- **调查交互**：先选择环境、时间区间、服务及获准租户，再执行有界查询。假设分别关联支持和反驳证据，保留未验证/否定结果及确认者；调查结束与工单解决是独立动作。
- **接入检查记录**：至少保存项目/环境、检查类型、连接配置版本、运行时间、结果和脱敏失败原因；配置变化使旧结果过期。没有日志样本只能说明当前无可用样本，不能据此判定关联成功或系统健康。
- **轻量服务目录**：按 I03 的实际需要维护服务与代码仓库、日志标签、Trace 后端及可信部署版本的映射。映射本身带来源与时间，不提前建设完整资产管理平台。
- **治理入口**：先把待审批、拒绝记录、操作回执及审计挂到相应工作流；权限矩阵作为配置视图。未知执行结果保留 Uncertain，不能因超时直接重试写操作。

保留已有取舍：独立管理员/员工账号是默认方式，外部 OIDC/SSO 可选；RAGFlow 是可替换的后续 Provider，不能成为首轮硬依赖；继续复用现有 PostgreSQL 任务机制，不因参考图中的 Redis 字样更换队列；MCP 作为受 Policy 约束的工具适配方式。参考中的第三方版本、许可与协议日期需在实际选型时另行查证，不据此变更依赖。

**下一批执行顺序**

1. K01 与 K05/K06 引用边界：完成主题/证据关系及兼容迁移，并先封闭客户发布引用暴露内部路径的缺口。验收旧文章/旧引用可读性、跨项目拒绝及客户响应不含内部证据。
2. K03：来源扫描后确认产品范围、手工修正主题和多来源映射；完成正式知识地图。刷新保留确认结果，跳过与未知可见。
3. K04—K06：主题驱动分层生成、业务资料补充、独立客户版本审核及黄金问题验证，保留现有文档历史和已发布版本。
4. S01—S05：持久对话、客户/员工工单页面、公开/内部隔离、解决方案回流。新增客户内容同步具备 S02 删除与保留语义。
5. I01 起：将既有日志/指标/Run 接入正式调查工作区，同时补真实接入检查和环境范围；Trace 与部署映射依实际接入情况推进。
6. E01—E03：在指标定义与授权完成后开放首个真实 Insights 场景。调度、SLA、更多连接器、可选 SSO 按后续包实施。

首页引导、角色导航和三个共享组件随对应业务包同步完善，不另等一次全面 UI 重做。每包均交付页面、真实接口、持久化、权限和失败路径；发布前再执行目标网站验收。上述为新增验收约束，尚不代表这些缺口已修复。

**里程碑与顺序**

| 里程碑 | 开发步骤 | 可交付结果 |
| --- | --- | --- |
| M1 知识中心首版 | 0 → 1 → 2 → 3 | 从一个真实仓库和已有业务资料建立分层文档，完成审核、发布与问答验证 |
| M2 持续支持闭环 | 4 → 5 → 6 | 刷新继续对话、上报生成工单、员工处理、客户跟进、解决经验进入知识草稿 |
| M3 持续更新与正式运行 | 7 → 8 → 9 | 变化影响和冲突可管理，团队与运行排查可持续使用，具备所承诺部署范围的运行保障 |
| M4 业务洞察 | 10 → 11 | 一个真实只读分析场景、可保存报告；随后支持调度和审核过的 Playbook |

第 4 步依赖 0/1，可在知识内容工作之外推进；工单页面不依赖高级冲突检测。第 10 步设计可提前，但正式开放须通过身份、数据权限和第 9 步相关门槛。默认按表顺序逐项交付。

**步骤 0：统一实体身份，固定迁移与验收基线**

- 工作：统一 `namespace/type/id` 合同及规范化、比较函数，覆盖 SDK、事件、失败恢复匹配、上报快照和证据关联；禁止模糊字符串拼接造成键碰撞。
- 兼容：旧数据缺少 namespace 时保留“未指定”，不能作为任意 namespace 的通配符。规范化键只在可信组织/项目/租户范围内使用，不作为授权凭据。
- 同时固定 `Source → SourceSnapshot → Evidence → KnowledgeTopic → KnowledgeDocument → DocumentRevision → Publication` 的关系。箭头表示可追溯关联，实际允许 Topic 关联多个来源证据，并产生内部、客户、API、排障等多个文档；文档不是知识的最底层实体。
- 定义 Case.type：SUPPORT_TICKET、MONITORING_ALERT、INCIDENT、AI_FINDING、MANUAL；所有类型共用证据、任务、分配、评论、解决方案及知识候选合同。此处只固定合同，不提前实现后续所有类型入口。
- 来源证据第一版即记录 Source/快照、源版本/commit、文件/行范围、内容指纹、observedAt、生成任务、模型身份与提示词版本；Source Revision 与 Deployment Revision 分离，没有部署证据时显示未知。记录数据迁移、API/SDK 兼容和回退策略。
- 验收：同类型同编号不同 namespace 不误关联，不互相清除失败；旧客户端仍可上报，历史 Case 可读；不扩宽租户权限。
- 主要位置：`packages/contracts`、`packages/web-sdk`、`packages/application` 及相应测试。

**步骤 1：员工身份、授权与正式后台骨架**

- 页面：独立账号登录、项目选择、权限不足页、修改密码；知识中心与支持工作台的共同布局；工作人员创建/停用、密码重置及项目授权配置。
- 后端：本地部署向导创建首位管理员，禁止公开注册和默认密码。提供安全密码哈希、服务端可撤销会话、登录限流、CSRF 防护、退出和密码重置；修改权限或密码后旧会话失效。先提供管理员、知识编辑/发布者、客服、工程人员、只读查看者等权限组合。
- 权限按组织/项目及明确租户范围约束；知识编辑与发布、客户回复与内部备注、普通信息与工程证据分别授权，服务端和数据库均落实。
- 本地 Owner 保留初始化与维护用途。远程工作台使用独立 Operator API/会话，不能代理现有本地访问码服务，也不能让 Operator 获得客户业务执行身份。外部 OIDC/SSO 不在首轮依赖中。
- 验收：客户 Token 不能登录员工后台；客服不能发布知识或读取未授权工程证据；员工撤权生效；跨项目和未授权租户均拒绝；管理操作记真实操作者。
- 主要位置：Server 鉴权/路由、Policy、持久层授权、Console；迁移 Setup 中可远程开放的职责，保留部署主机专属操作。

**步骤 2：知识接入向导与产品知识地图**

- 页面流程：选择项目 → 连接来源 → 扫描预览 → 确认产品范围 → 编辑知识地图 → 选择补充资料 → 查看生成任务。
- 来源分三类：工程资料（代码/OpenAPI/配置等）、业务资料（操作指南/FAQ/SOP/规则等）、经验资料（后续工单与排查结论）。首版实现 Git/目录、Markdown/TXT 导入和手工录入；其他类型明确提示支持状态。
- 仓库连接提供只读凭据引用、连接测试、固定 ref/commit、包含/排除范围及受众配置；密钥只保存在服务端。先覆盖一个实际项目技术栈，不承诺所有语言语义分析。
- 扫描报告展示真实识别的应用/模块、候选领域、文件及解析覆盖、跳过原因、预算和模型出站范围。用户确认哪些模块属于产品，再生成目录。
- 默认文档层次：产品与领域、用户指南、API、工程架构、运行维护；按业务域组织并允许重命名、合并、排除。业务分类和客户/内部受众是两个独立维度。
- 后端：增加可持久跟踪的扫描/分析/生成任务，支持进度、取消、失败说明和恢复；复用现有队列/租约机制，但不强行制造客户 Case 来承载索引任务。
- 验收：一个真实仓库配两类业务资料可全程在界面完成接入；刷新仍可查看任务；超预算或不支持的文件明确可见；未完成构建不替换已发布知识。
- 主要位置：`packages/knowledge` 扫描/索引、Setup 来源能力、Console 新知识页面、任务与持久层。

**步骤 3：分层文档生成、补充、审核、发布与问答验证**

- 页面：知识总览、可浏览的目录树/文章页、文档编辑器、草稿、审核队列、已发布版本、问答验证台。支持按领域、层次、来源、受众和状态筛选；不是仅展示构建记录或配置 JSON。
- 首页围绕 Product Understanding：列出已确认业务域及概念、规则、用户指南、API、错误码、排障条目的可核对数量；点击领域查看来源、缺口、待审核与变化。只有存在明确分母和判定规则时展示覆盖率，并解释计算方式；不显示模型主观的“理解百分比”。
- 生成：沿知识地图分层生成产品概览、业务规则、用户操作、API、架构和排障条目。模型结论区分“实现证据”“人工确认的业务规则”“待核实推断”；文件存在或局部分支不能证明完整业务语义。
- 知识模型：稳定 KnowledgeTopic 关联多个快照和 Evidence，再生成稳定 Document ID、不可变 Revision 与独立 Publication。文档保存适用产品版本、受众/租户、责任人、审核与发布记录；具体事实/段落关联证据，区分直接证据、人工规则和推断。保留旧 build/article 引用，平滑迁移，不重新编号破坏历史 Case。
- 补充：管理员可以导入现有说明、手工补写、把多个来源挂到同一主题、登记缺口或解释暂不适用。文章重新生成进入新草稿，展示差异，不覆盖人工编辑。
- 发布：先做逐篇审核，再以明确的发布集合切换可见版本；失败保持上一版，撤下和回滚可核对。跨多来源生成的文档不得被某个 source 的 active build 隐式替换。
- 客户版本：源码派生默认内部；对外生成单独脱敏草稿，分别审核。客户引用指向获准公开的文档，不暴露内部路径、源码片段和受限工单。来源撤销须同步评估并收紧派生内容与历史引用访问。
- 问答验证台：按获准模拟的角色/租户预览可见答案、引用、未命中、耗时与模型成本。首轮维护 20 个黄金问题：5 个产品概念、5 个业务规则、5 个用户操作、3 个 API/错误、2 个故意不可回答；逐步扩到 50 个。每次 rebuild 自动比较候选与当前发布版的可回答性、正确证据、受众、禁止来源泄露和不可回答问题的幻觉。内部评测不能使候选文章对客户提前可见；事实正确性保留人工标注，不只依赖模型打分。
- 验收：能从业务域目录阅读一套分层文档；每项重要规则可追溯；未审核内容不会用于客户回答；重生成保留人工修改；客户无法追溯进内部证据；模型不可用时有明确状态或原文路径。

**步骤 4：持久 Conversation**

- 页面：客户历史对话列表、恢复/新建/归档/删除、当前对话关联的查询、操作提案与工单。刷新或换页后可继续。
- 后端：独立 Conversation/Message/Turn，消息顺序、幂等键、分页、调用中断状态；保留用户/助手消息和业务结果引用。Conversation 可关联多个 Case，创建 Case 时关联选定消息快照，不默认暴露整段聊天。
- 数据：历史展示不等于全部放进模型；定义上下文预算和脱敏摘要。查询结果历史明确标记时间，重新获取使用当前权限；知识、截图和证据引用在读取时再次授权。
- 身份与删除：仅允许同一可信用户范围恢复；退出/切换身份清理浏览器状态。从第二阶段起引入 conversation、ticket、attachment、runtime_evidence、audit 五类保留策略，客户内容可配置期限，运行证据可采用较短期限，审计独立保留。支持删除对话、删除附件和脱敏敏感内容；定义关联工单保留例外、索引/缓存失效及备份恢复后的删除处理，不随聊天删除必要审计。
- 验收：刷新、多标签页、断网重试、重复消息和服务重启不串线；恢复聊天不会自动重执行业务写入；跨用户/租户不可见；删除语义有真实存储验证。
- 主要位置：`packages/application`、新增持久层迁移、Server、SDK/widget/独立支持页。

**步骤 5：客户工单页与员工工单工作台**

- 客户页面：“我的工单”列表与详情，有可读编号、主题、状态、最近更新、公开消息、补充说明、解决结果及重开入口；从上报成功回执和历史对话直接跳转。
- 员工页面：工单队列、筛选/搜索/排序/分页；顶部提供客户/租户、页面、完整实体身份、业务事件、requestId/traceId、环境与应用版本的上下文摘要，并标记线索是否验证。详情包含客户沟通、内部备注、调查证据、AI 假设、操作时间线、负责人/优先级/标签，以及解决方案和知识回流入口。窄屏按标签切换，不强制挤成三列。
- 数据：保留 Case 主体并实现 SUPPORT_TICKET 类型，增加编号、来源、优先级、负责人、团队及版本化处理记录。类型与来源独立，例如 AI 转人工产生的仍可以是 SUPPORT_TICKET。旧客户报告映射该类型，监控对象保留原身份并显式关联；公开回复与内部备注在数据模型/API/存储授权上分离，不依赖前端隐藏。
- 生命周期：首版使用新建、处理中、等待客户、等待内部、已解决、已关闭，支持有权限的重开。明确转移权限；旧 open/needs_human 映射新建并保留历史含义，resolved 映射已解决，不虚构旧处理记录。
- 工单状态独立于 Run 状态；排查完成不等于客户问题解决。监控异常先关联/转为 Case，不把一次监控样本变成一张工单；团队级事故与客户工单的可见范围分别定义。
- 分配先实现个人接手与负责人；SLA 与复杂路由放到第 8 步。客户默认只看自己的工单，租户管理者能否看其他成员须另行授权。
- 验收：一次上报可靠生成一张工单；刷新可读、支持人员可接手回复；内部内容不泄露；并发分配/状态变化可检测；客户看见解决结果且可重开；审计记录实际员工。

**步骤 6：解决方案回流知识**

- 页面：工单解决时填写症状、已验证原因/未知、临时处理、长期处理及证据；提供“生成知识草稿”。可生成内部排障版，再另行生成客户 FAQ 版。
- 后端：将 resolution、公开回复、获准证据转为文档候选；查找相近文章，供选择新建/更新/放弃。相同 resolution 重试不重复生成，工单后来重开会标记候选需复核。
- 内部与客户版本保持独立审核、来源追溯和撤销传播；日志、个人信息及私有业务值不直接复制到公开文章。
- 验收：一个真实受控故障从对话生成工单，经证据排查、员工解决后生成草稿；审核发布后能回答同类问题；未审核草稿和内部证据不进入客户回答。

**步骤 7：知识新鲜度、冲突与缺口管理**

- 页面：来源更新、受影响文档、待复核、冲突列表/详情、知识覆盖矩阵。用户可以比较证据、修订文章、记录有效范围、推迟或关闭候选冲突。
- 新鲜度：比较固定快照，通过文档到代码/来源的证据关系计算影响范围；显示变化 commit 和受影响段落。先做可解释的文件/片段级检测，再按需求增加符号级分析；大规模重构无法判断时标记未知。
- 区分仓库最新版本和实际部署版本。同一文档可有不同产品版本/环境的适用范围；代码变更不自动宣判旧线上文档错误。
- 冲突：先识别有相同概念、单位、版本和适用范围的明确参数/规则冲突。规则与模型生成候选，由人员裁决；仅代码与文档不同不一定是冲突，不按置信度自动覆盖。
- 过期不默认等于撤下：展示新鲜度，按影响程度设置重新审核/暂停发布规则；明确权限收紧或来源撤销则立即执行访问收紧。
- 缺口：分别展示无实现证据、无客户说明、无排障文章、来源不可解析、待审核等状态；不声称能证明所有业务知识已覆盖。
- 验收：相关源码变化只触发可解释的复核范围；无关变更不重复生成全部文章；20MB/10MB 等同范围矛盾进入冲突队列，不自动选边；人工编辑与发布历史保留。

**步骤 8：团队处理、外部协作与更深运行排查**

- 工单团队：团队队列、转派、关注、站内通知、SLA 策略。定义工作时间/时区、等待状态暂停规则、首响与解决时限及升级记录；不要只加一个倒计时字段。
- 外部协作：选择一个实际工单/通知系统；复用 outbox，定义 eventId、签名、重试、死信/重放、去重、乱序和回写循环处理。分别明确外部系统与 Agent18 哪一方主控状态。
- 排查页面：展示已有关联 Case/Run/日志/指标；根据试点需要增加一个 Trace 后端及部署版本到源码 commit 的可信映射。缺失采样/版本映射显示未知。
- 验收：多员工协作不丢回复；SLA 暂停/重开结果可核对；外部投递重复与乱序可恢复；能从一个真实失败请求找到对应证据，工程内容与客户摘要分别授权。
- 三项可独立交付；外部连接器或完整 Trace 不作为知识中心、基本工单和首条 Insights 的硬依赖。

**步骤 9：正式开放门槛与真实项目验收**

- 持续补充 Agent18 自身请求/依赖/模型/队列遥测、成本预算、速率限制和故障诊断，不默认记录正文或凭据。
- 提供可重复构建/分发产物，验证从 0.8 升级、旧 Case/知识/提案读取、迁移失败保护、备份、隔离恢复和回退。发布公共镜像/SDK 时再公布真实地址与版本。
- 实现并验证各类数据的保留/删除、凭据轮换与撤权、审计访问和模型出站配置。第 4 步新增聊天即带最小删除机制，本步统一管理截图、报告和其他数据。
- 若交付仍限定单机，明确容量、维护窗口与恢复目标；若承诺多实例，先完成共享配额/租约、迁移互斥、配置一致性、公平调度和故障恢复验证。
- 以一个真实成熟网站完成跨仓库验收：知识生成/补充/发布 → 真实身份问答 → 实时查询 → 确认写入及业务回读 → 故障上报 → 工单处理 → 知识回流。
- 出口：填写目标系统接入报告，记录通过/失败/未接入、负载与延迟/成本样本、许可用户范围及关闭入口/停用能力/恢复步骤。单元测试和合成 CI 不代替此验收。

**步骤 10：Insights 首个只读场景**

- 先选一个实际业务：网站访问/转化/错误趋势，或经营订单/销售额趋势。根据目标 SaaS 的真实需求选择，分别定义统计口径，不混用访问事件、业务收入和运行指标。
- 页面：提问、参数确认、报告详情、保存的报告。报告包括时间区间/时区、指标定义、趋势/对比、数据来源、查询时间、过滤范围、缺失/截断说明和相关业务入口。
- 后端：Insights 是现有 Tool/Policy/Evidence/Run 的一种用途，不另建分析 Agent、权限系统或连接器运行时。以 `MetricDefinition + 已审核 READ 工具 + 有证据的 Insight` 为第一版基础，增加 MetricResult 与报告合同。先接现有 SaaS 聚合 API 或一个已有分析服务，不向模型开放任意 SQL、任意 URL 或任意生产库权限。
- MetricDefinition 必须版本化：记录业务定义、数据源/工具版本、单位/币种、时区、退款/取消处理、分母、比较周期、完整性及新鲜度；每份报告固定所用定义版本，口径变化不能静默重算历史结论。数值和变化率由确定性计算得到，模型负责解释，不虚构计算结果。
- 先支持查询、分组、趋势与描述性解释；“为什么下降”只提出有证据的假设，相关性不等于因果。保存报告/导出/重读仍校验当前授权，不因聚合而取消租户及字段权限。
- 验收：至少三个代表问题与原系统统计逐项对账；跨租户、撤权、空数据、不完整周期、零分母和服务失败正确处理；不因上下文或模型建议产生写操作。

**步骤 11：周期洞察、Playbook 与受控行动**

- 页面：保存分析模板、定期报告、执行记录、失败重试和暂停；有需要时增加建议行动的具体预览与确认。
- 调度：服务端保存经批准的范围与执行身份，执行时重新检查权限、配额和数据源状态，不保存客户短期 Token 作为长期任务凭据；任务拥有者撤权后暂停，通知收件人单独授权。
- Playbook：先独立验证经营表现、网站转化等至少两个真实场景确有共同的收集、计算、对比、解释流程，再抽象所需工具/版本、参数、范围、预算、输出和确认点。当前不做 Marketplace、通用 DSL 或另一套运行时；导入声明不自动安装或执行不可信代码。
- 由洞察触发写操作时，进入已有提案/确认/回执链路；调度器或只读 Run 不获得直接业务写权限。群发、付款等保留宿主原有审批和额度规则。
- 验收：重启/重复触发不重复生成有效任务；报告可追溯输入与工具版本；权限撤销和工具定义变化阻止继续执行；用户仅查询分析时绝不发送消息或修改业务。

**更后续的独立项目**

在问答评测证明召回瓶颈后接入替代检索 Provider；在真实用户需求出现后扩展网站/PDF/第三方资料和分析连接器。代码修复单独按证据交接、修复建议、隔离测试、草稿 PR 推进，不把自动改代码、合并或生产发布作为上述里程碑的默认承诺。

**每一步的完成标准**

每一步交付可操作页面及真实 API/持久化行为，包含首次进入、无数据、加载、失败、重试和权限不足状态。记录需求到界面/合同/存储/测试/目标项目证据的对应关系；覆盖正常、拒绝、未知和恢复路径。新增模型能力使用真实样本记录质量、成本与局限；无模型路径不得冒充语义分析成功。

执行状态另见开发记录；本计划中的定义和验收要求不等于功能已实现，公开能力表只在实现和验证完成后更新。
