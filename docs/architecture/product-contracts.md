# 产品领域合同与演进方案

状态：设计基线，2026-09-18。以[总计划](../planning/product-development-plan-20260918.md)为产品范围；只有开发记录明确验证的部分属于已实现能力。

**1. 四条产品主线和共同基础**

Understand 管理产品知识，Support 管理对话与工单，Investigate 管理证据与调查，Empower 提供洞察及经确认的业务行动。四者共用身份、上下文、工具登记、策略、证据合同、任务机制和审计；不再为每条主线引入一套账号、权限或 Agent 运行时。

网站客户由宿主签发 Support Token；Agent18 工作人员使用独立账号。平台管理员可管理本部署的项目和工作人员，不因此获得客户业务写入身份。宿主员工 SSO 属于未来可选接入，不是实施前置条件。

**2. 知识领域模型**

| 对象 | 职责与关键字段 | 必须保持的约束 |
| --- | --- | --- |
| Source | 来源配置：项目、种类、位置/凭据引用、范围、受众、允许租户、责任人 | 私密凭据不可进入文章、模型输入或日志；关闭来源先收紧读取 |
| SourceSnapshot | 固定内容快照：sourceId、源版本、commit（可空）、文件清单/指纹、读取时间、覆盖报告 | 不可变；目录指纹不能冒充 Git commit；一次失败读取不创建可发布的完整快照 |
| SourceEvidence | 可核对的事实来源：snapshotId、路径/行范围或其他定位、内容指纹、受众、证据类型 | 引用必须指向实际读取内容；租户/受众范围不从模型结果取得 |
| KnowledgeTopic | 稳定的产品主题：topicId、业务域、topicKey、名称、父主题、人工确认状态 | 一个主题可关联多个来源，也可没有文档；标题变更不改变 ID |
| TopicEvidence | 主题与证据的多对多关系：topicId、evidenceId、关系类别、人工确认、适用范围 | 关联不是事实成立的证明；保留推断与人工业务规则的差别 |
| KnowledgeDocument | 主题的呈现方式：documentId、topicId、层次、受众、语言、标题、责任人 | 同一 Topic 可有内部、客户、API、排障等不同文档；受众不是层次 |
| DocumentRevision | 不可变内容：documentId、revisionId、正文/结构化段落、事实到证据链接、适用版本、generationRunId、模型/提示词版本、编辑者 | 人工修改产生新修订；生成不覆盖人工文本；旧版本可追溯 |
| ReviewDecision | 对具体修订的审核：revisionId、审核人、决定、理由、时间 | 新修订不继承旧审核；审核资格按项目/受众实时校验 |
| Publication | 可见发布集合：channel、产品版本、文档修订集合、发布时间/发布者、上一发布版本 | 发布与受众按一个事务切换；读操作只查有效发布；撤下即时影响后续检索 |
| DeploymentRevision | 部署映射：环境、release、源仓库/commit、证据来源、验证时间 | 与 SourceSnapshot 的版本独立；缺失时为未知，不能使用当前 HEAD 补齐 |

Topic、Document、Revision、Evidence、Publication 的引用同时包含可信 organization/project 范围，外键或等效约束阻止跨项目引用。Topic 可以跨来源，但跨项目复用必须显式复制/授权，不做隐式合并。租户限定资料的数量、标题和缺口状态也不能泄露给其他租户。

**3. Evidence 复用边界**

现有 `core.evidence` 依赖 Case/Run 外键，不能直接作为所有源码证据的存储表。复用共同的 Evidence envelope、来源追溯和可见性校验；增加项目范围的 `knowledge.source_evidence`，运行证据仍保留在 `core.evidence`。两类证据通过显式关系引用，不为每次知识扫描创建虚构客户工单。

工单经验导入知识时保留 Case/Run/Evidence ID、当时的范围和内容指纹。它首先进入内部候选，客户版通过单独脱敏和发布审核形成可公开文档。面向客户的引用只暴露可公开文档，不能反向打开内部源码或客户原始问题。

“Confidence: High”不能代替证据或审核状态。事实状态至少区分直接证据、人工确认、待核实推断；源代码局部分支不足以证明完整用户规则。

**4. 来源变化与内容生命周期**

来源状态：待配置、连接失败、可读取、已暂停。快照/任务状态：排队、读取、分析、完成、失败、取消。文档审核状态：草稿、待审核、退回、通过。发布是独立事件，知识新鲜度也独立标记，不把所有状态塞进一个枚举。

每次重建固定输入快照、Topic 选择、生成配置及模型/提示词版本。代码变化产生受影响候选；管理员可接受新稿、继续编辑或保留旧版并写明理由。已有人工修订参与差异比较，不被后台 watch 静默覆盖。

缺口统计依据已确认 Topic 的必要文档类型和已核实证据。比如“客户指南 6/10 已发布”有明确分母，可以展示 60%；“理解了产品 91%”没有可验证含义，不展示。

发布前检查：修订审核通过、证据可读取、受众合法、适用版本明确或显式未知、必要质量门槛通过。发布使用幂等键和预期版本，过期审核或并发版本变化返回冲突。来源撤销/租户收紧先执行访问收紧；派生文章和历史引用不能仅凭旧发布状态继续泄露受限内容。

**5. Conversation 与 Case**

Conversation 包含 Message、业务查询结果引用、ActionProposal 引用和 CaseLink。Message 有稳定序号、幂等键和内容可见性。关联工单使用指定消息快照，不直接把整个会话复制给所有员工。

Case.type 的设计值：SUPPORT_TICKET、MONITORING_ALERT、INCIDENT、AI_FINDING、MANUAL。来源 source 独立记录客户、AI 升级、监控或人工创建；AI 转人工仍可产生 SUPPORT_TICKET。第一轮实现客户工单，其他类型按真实链路逐步开启。

共用 Assignment、Comment、Resolution、Run、Evidence 和 KnowledgeCandidate 合同，但不同类型的范围和转移规则可以不同。客户工单默认属于单个客户身份；团队事件不伪造客户 subject。现有 `__operations__` 等内部标签不能当作真实客户或自动授予读取权限。

公开回复、内部备注、工程证据分别授权。工单的“已解决”来自处理决定，不能由 Run completed、一次健康检查或模型措辞自动推导。

**6. 最小数据治理**

| 分类 | 最小操作 | 关联数据处理 |
| --- | --- | --- |
| conversation | 可配置保留、归档、删除 | 删正文及索引/缓存；关联工单是否保留消息快照必须明示 |
| ticket | 保留策略、敏感文本脱敏、必要删除 | 解决方案引用脱敏/失效；避免删除必要业务回执或审计 |
| attachment | 单独删除、过期清理 | 清除原图/派生预览/访问链接；历史引用显示已删除 |
| runtime_evidence | 较短期限、按范围删除 | 原日志在外部系统时仅删除本平台副本/摘要，分别记录责任 |
| audit | 独立保留、受控导出 | 不记录密码/Token/原文；不跟随聊天一并删除 |

从 M2 第一个持久对话功能起实施，不等企业治理阶段再补。删除任务持久化并可重试；记录墓碑或等效删除清单，恢复备份后重新落实已生效的删除要求。具体保留天数由部署者配置，不在代码中假设所有项目相同。

**7. 兼容和迁移**

现有 Sources/Builds/Articles 保留原 ID。先增加新表与映射，再回填可证明的关系；旧文章可映射为 legacy 文档，但未经审核不能推断其业务 Topic 或生成未知来源证据。历史 provenance 缺失显示未知，不用迁移时间冒充原始观察/生成时间。

读取路径先支持旧发布与新 Publication，使用明确优先规则和测试，禁止同一文档重复召回。新知识审核/发布权限不能直接授予工作人员 indexer 数据库凭据。迁移先在隔离库演练，活动环境需要备份及明确发布范围；回退使用对应版本和隔离恢复，避免旧代码误读新发布语义。

**8. Metric Definition 与 Insights**

MetricDefinition 是指标口径：稳定 ID、版本、业务定义、来源工具版本、单位/币种、时区、过滤规则、退款/取消处理、分母、允许维度、最新数据时间及新鲜度目标。MetricResult 保存本次查询的范围、口径版本、数据时间和确定性结果。

Insight 关联 MetricResult/Evidence 和解释生成任务。计算数字、同比/环比及分母处理由程序负责；模型只能解释获准结果。历史报告固定口径版本，重新运行生成新版本。需要写入时创建已有 ActionProposal，不新增可绕过确认的 Analytics 执行入口。
