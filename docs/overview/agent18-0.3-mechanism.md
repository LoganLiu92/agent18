# agent18 0.3：整体运行机制与实现综述

> 后续的初始化与界面能力见 [0.4 安装与接入综述](agent18-0.4-experience.md)。本文保留 0.3 底层机制说明。

日期：2026-09-15。本文描述仓库当前代码和本地验证范围，取代 0.2 历史综述中的能力状态。项目面向有既有网站、后端、代码库和产品文档的 SaaS：用这些资产建立可追溯知识，在现有页面里提供问答、支持调查与用户授权的业务操作。

## 一、系统组成与职责

| 组成 | 实现 | 职责与边界 |
|---|---|---|
| 网站 SDK / 可选面板 | `packages/web-sdk` | 获取 SaaS 短期身份、显式页面上下文、提问、报告问题、预览及确认操作 |
| 客户 Console | `apps/console` | 演示身份切换、问题列表、Run 历史、知识目录/问答、业务助手、接入状态 |
| Core HTTP 服务 | `apps/server` | 验证身份、绑定项目/租户/用户、校验 DTO、审计、知识与业务编排、SDK 静态资源 |
| 知识构建器 | `packages/knowledge` + CLI | 读目录/Git、过滤、分块、分类、模型整理、增量缓存、构建报告、发布和撤下 |
| 模型适配器 | `CompatibleModel` | 部署者 BYOK；只接受结构化文本生成，不给模型工具或基础设施凭据 |
| 业务操作服务 | `packages/actions` | 注册表和参数校验、预览、确认、配置复核、结果持久化与回执核对 |
| SaaS 业务桥 | SaaS 自己实现；仓库有示例 | 用户及对象授权、业务规则、真实写入、版本控制、幂等回执 |
| OPA | `packages/policy/rego` | 知识读取和受确认的业务委托策略；缺输入或服务不可用时拒绝 |
| PostgreSQL | `packages/persistence` | 核心业务与 RLS、知识版本、审计、outbox/调度元数据 |
| Worker / pg-boss | `apps/worker` | 从持久队列领取只含 dispatch ID 的任务，请求 Core 执行支持调查 |

默认 Compose 包含 PostgreSQL、OPA、一次性 migration、Core、Worker 与独立 demo SaaS；Core 开放本机 4318，demo SaaS 4319，PostgreSQL 54328，OPA 8188。知识 CLI 在宿主机运行，使用独立 indexer 数据库角色。源码不挂载给 Core/Worker，也不会被自动执行。

## 二、知识从哪里来，怎样变成体系

1. 部署者配置多个来源：本地源码/文档目录，或具有只读访问权限的 Git 仓库和 ref；每个来源明确内部/客户受众及允许的租户。
2. 扫描器跳过隐藏文件、依赖、构建结果、符号/硬链接、二进制及匹配密钥特征的内容，并执行文件数、单文件、总量、遍历和分块上限。Git 只读 commit 对象，不执行仓库代码。
3. 文件按标题、行和长度分块，保留相对路径、起止行、内容指纹与版本。目录版本是内容清单指纹，Git 版本是 commit SHA。
4. 原文模式按文件/标题/类别生成可查询条目，不调用模型。模型模式按同文件最多 8 个片段一组，生成结构化知识文章，分类为概览、架构、接口、业务流程、配置、排障。每篇必须引用提供的片段 ID；任何伪造引用导致该构建失败。
5. 模型输出缓存按完整输入、提示词、模型配置与受众识别。没有变化的组复用结果，节约增量同步成本。每个来源每轮有明确的模型调用预算；超额保留缓存供下轮使用，但不激活半成品。
6. 构建落库为 `building → ready / failed`。操作者导出文章审核，再发布指定 build。发布事务只切换该来源的活动 build，一次完整生效；失败保留旧版本，可重新发布旧版本回滚。
7. 客户目录与检索只读取当前活动、客户受众、当前项目/租户可见文章。内部条目只可由部署 CLI 导出审核。发布切换/撤下后，旧 Case 引用也会重新经过可见性过滤。

这是一套自动归类、有来源的知识构建基础。当前没有代码调用图、AST 深度理解、向量语义检索、跨仓库全局推理、上传解析或自动文件监控；模型的语义准确度和面向客户的内容范围仍需审核，不能把全代码导入等同于“所有业务知识已经完整正确”。

## 三、用户提问与知识回答

网站先从 SaaS 后端获取签名 Support Token。Core 根据可信项目配置验证 issuer、audience、EdDSA、公钥、最长 10 分钟有效期、项目 claim，再从 Token 读取租户和用户。客户不能覆盖这些授权范围。随后检查已注册租户并进入具备事务级范围变量的数据库查询。

知识操作先经过 OPA，再提交审计，然后查询 PostgreSQL 文章 GIN 索引。当前检索为英文词/代码标识符与中文双字词的重合排序，最多返回 5 条；不需要额外向量服务。返回 DTO 去除内部 scope，仅保留标题、摘录、来源、版本和观察时间。

问答接口在这一步之后，可把问题与可见引用发送到部署者配置的模型。模型不得调用工具，输出必须是 JSON，回答必须引用检索结果里的 ID。响应超时、过大、拒绝、JSON 错误、未知引用都会停止返回生成答案。返回前再次检查来源可见性；如果构建被切换或撤下，则要求用户重新查询。

没有模型时诚实返回原文；没有资料时提示缺少依据，不生成无来源业务答案。Core 对问答/规划/操作请求实施单进程 4 个并发、每身份每分钟 20 次的基础限额。这不是多实例全局配额或费用预算系统。

## 四、代客业务操作怎样运行

| 阶段 | 输入与结果 | 持久化/校验 |
|---|---|---|
| 发现 | 当前身份可见的已启用操作、参数表单 | 部署配置注册表 + 当前角色 |
| 规划（可选模型） | 用户描述 → 单个操作 ID 和参数 | 仅当前允许列表；缺字段要求补充；不执行 |
| 预览 | SaaS `prepare` 返回变更摘要和业务版本 | SaaS 验证权限；Core 保存精确参数、预览、注册表哈希与 5 分钟期限 |
| 确认 | 用户对指定 proposal 点击确认 | 新请求身份、同租户同用户 RLS、期限、角色、配置哈希、OPA |
| 发出执行 | 先提交 `executing` 与确认审计，再调用 SaaS `execute` | 同一提案行锁只领取一次；Token 仅当前内存转发 |
| 业务提交 | SaaS 再查权限/对象/版本，将变更和幂等回执一起提交 | Core 无权替 SaaS 跳过校验 |
| 结果 | `succeeded / rejected`；异常时 `uncertain` | 回执字段和大小校验、结果与审计事务 |
| 核对 | `status` 只查询原幂等键回执 | 不重发写操作；缺回执继续不确定 |

提案记录按项目/租户/用户持久化，页面刷新后可从最近操作恢复查看。重复确认不会重发已有提案。新提案是新幂等键，系统不能自动判断任意两份自然语言请求是否指同一业务意图；业务桥仍需实现业务级去重和约束。

仓库提供独立 SaaS 示例：修改当前用户的通知偏好，SaaS 自己用 SQLite 存储偏好和回执，执行前比较版本，数据与回执同事务提交。示例只改变偏好开关，不实际发邮件。现有网站接入时用自己的业务接口替换它。

## 五、支持报告与持久调查

这部分继承 0.2 的完整链路，并把知识 Provider 升级为按项目选择 fixture/真实索引：

- 客户提交问题和显式页面上下文；Core 在同一事务中建立 Case、Run、能力范围、dispatch outbox 和审计。UUID 幂等键重复返回原记录，参数冲突则拒绝。
- Dispatcher 从持久 outbox 投递 pg-boss；Job 仅有 dispatch ID。Worker 只有队列凭据和 workload token，不能读取业务/知识数据库。
- Core 根据 dispatch 映射和 60 秒 lease 恢复范围，使用 Run advisory lock 防止同一调查并发执行。已审核的 `knowledge.search` 经 OPA 和审计后才能调用 Provider。
- Run 记录每次开始、读取、结果、异常、中断、取消；每 Run 至多 3 次尝试，当前每次执行预算 5 秒，知识读取最多 3 秒，能力期限 1 小时。
- 用户可取消等待/执行中的调查，撤销结果提交资格；失败或取消后可创建新 Run，Case 总共最多 3 个 Run。策略阻断不开放客户重试。
- 队列失败、完成但无终态、丢失等情况通过持久记录核对，避免 Case 永久悬空；应用或 Worker 重启后通过 outbox 恢复。

当前调查只做知识检索，仍需人工跟进，不声称已经自动排查日志或完成代码修复。知识模型问答是独立 HTTP 路径，没有塞进 5 秒 Run 预算；业务写操作也是独立提案状态机，避免把读任务的自动重试套到业务写入。

## 六、权限、存储和运行边界

| 角色/位置 | 可访问内容 |
|---|---|
| 浏览器 | 短期用户 Token、当前可见 DTO、可执行操作与预览 |
| Core `agent18_app` | 受 FORCE RLS 保护的 Case/Run/Evidence/Audit/Action；当前可见知识；不拥有表 |
| Worker `agent18_queue` | pg-boss 队列 DML；没有 Core/knowledge 表权限 |
| 索引 CLI `agent18_indexer` | 指定组织/项目的知识来源、构建、文章和缓存；没有客户 Case/审计权限 |
| 一次性 migrator | 数据库角色、DDL、元数据注册；不挂载到运行服务 |
| SaaS 业务桥 | 自己的用户会话/授权、业务数据与幂等回执 |
| 模型供应商 | 部署者配置允许发送的源片段、客户问题或操作列表；没有直接数据库/执行权限 |

证据、执行步骤、审计对 Core 角色只允许追加或读取；管理员仍能改数据库，因此不宣称密码学防篡改。知识文章在源受众策略下对同租户用户共享；Case 和操作提案还按用户隔离。源码生成内容默认内部，显式发布为客户内容前需要检查其可公开程度。

配置生成在 gitignored `.local`，私钥只给 SaaS issuer，Core 只拿公钥。容器非 root、根文件系统只读、移除 Linux capabilities；生产仍需自行完成身份桥、TLS、备份、密钥管理、权限撤销和业务适配验收。拥有源码和部署权限只是接入条件，不替代这些业务规则。

| 能力 | 关键文件 | 主要验证 |
