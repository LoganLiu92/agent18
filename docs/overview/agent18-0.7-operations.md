# agent18 0.7：支持、业务操作与运行排查

agent18 是部署在现有 SaaS 旁边的支持服务。客户只需要一个对话入口；部署者在本机工作台配置知识、业务能力与监控数据源。0.7 在已有知识、身份、查询和确认办理的基础上，增加页面上下文、真实 Loki / Prometheus 连接、工单自动排查、周期巡检和内部经验草稿。

这是源码自托管的集成预览版。下表区分实际行为和接入方需要提供的内容，避免把代码仓库和模型 Key 当成所有权限与业务语义的替代品。

| 场景 | 已实现的运行行为 | 接入方提供 |
| --- | --- | --- |
| AI 客服 | 文档/Git/目录扫描、版本化知识、引用问答、持续追问、无答案转支持 | 客户可见资料、审核发布、模型 Key；内部代码默认不向客户公开 |
| 业务 Agent | 在当前实体上下文下补参数；只读查询；增删改通过注册动作的预览、确认、执行、回执协议 | 真实用户 Token、受限业务定义、SaaS 对象权限和事务幂等实现 |
| 问题上报 | 收集页面路径、可见文字、错误、交互线索与可选脱敏截图，预览后随工单提交 | SDK 挂载、敏感区域标记、路由/实体/traceId 的显式关联 |
| 自动排查 | 工单事务中登记任务，Worker 调度固定健康检查和 Loki / Prometheus 查询，生成引用证据的分析与建议 | 监控地址、只读凭据、项目/租户标签、指标表达式 |
| 周期巡检 | 持久调度、失败/未知区分、重复异常合并、人工接手、健康证据触发恢复 | 部署者选定检查与阈值，持续运行 Core / Worker |
| 经验沉淀 | 排查报告导出内部 Markdown 草稿，再进入已有知识审核发布流程 | 人工核实原因、补充处理结果、确认知识受众 |

“增删改”是业务桥允许注册的动作类型，演示项目展示订单通知修改。任意原系统 REST 写接口不会自动变成可执行工具：接入者需要适配准备、执行和回执合同。实际执行调用 SaaS 后端 API，没有自动点击网页、直接写 SaaS 数据库或共用管理员身份的执行器。

## 一次用户请求如何运行

1. SaaS 根据当前真实登录会话签发短期 Support Token。Core 验证签名、issuer、audience、项目、租户和用户；浏览器中的实体、traceId 与环境字段仅是线索。
2. 对话路由根据可用目录选择知识、查询、业务提案或问题上报。比如“查看当前订单”，可以从 `context.entity` 补入匹配的 `orderId`；SaaS 仍复核该用户是否有权访问对象。
3. 知识问答使用已发布、当前允许访问的文章与来源引用。代码扫描可帮助生成知识，但不能保证覆盖所有问题或答案正确；找不到可靠依据时继续澄清或上报。
4. 写操作先生成包含具体字段变化和版本的提案。客户明确确认后，Core 再校验并调用业务桥；SaaS 把业务变更和幂等回执同事务保存。不确定结果保持待核对，避免自动重复写入。
5. 上报时，浮窗自动准备一份页面上下文，客户可展开检查或取消附带。Case、捕获内容、原有知识 Run/outbox 和新增排查任务在同一数据库事务中持久化。重复提交相同幂等键不会产生第二份任务。
6. Worker 通过独立 workload 凭据触发排查。Core 从已保存配置取得地址与选择条件，通过工具注册中心、OPA 和 Gateway 执行只读观测。客户不能选择内部 URL 或直接调用 `operations.observe`。
7. HTTP 保存状态码和耗时；Loki 查固定项目标签，工单模式追加真实租户、可选用户标签与 traceId；Prometheus 执行部署者保存的表达式。返回数据有时间、大小、条数、scope 和 schema 校验。
8. 规则先整理异常、未知项与下一步；启用模型分析后，仅发送有界、脱敏的证据摘要和页面错误。模型必须引用存在的 Evidence ID，失败时回退规则。输出是待验证的假设，不能等同已证明根因。
9. 工程证据只在 Owner 工作台展示。客户看到排查状态和不含日志的计数摘要，支持人员核实后可通过已有工单回复解释结果。内部报告可以整理为知识草稿，但不会自动公开或自动修复线上系统。

## 巡检和故障恢复机制

Worker 每 10 秒尝试调度，项目巡检间隔可设为 60 秒至 24 小时。`control.observation_schedules` 保存下次计划；`observation_jobs` 保存任务状态、配置指纹、尝试次数和租约。数据库锁避免多个调度者同时领取；单次处理一份任务，工单任务优先。进程中断后租约到期可重新领取，最多三次。仍在活动配置中的项目若禁用检查或配置变化，排队中的旧任务会取消；不属于当前 Core 项目配置的任务不会被它领取或取消。移除项目后保留历史和待处理记录，重新接入时再校验指纹。

每个项目最多八项固定检查。失败、无数据、非有限数值、过期指标或无权访问返回“无法确定”，不能冒充正常。`observation_incidents` 按项目和检查 ID 合并，持续异常增加出现次数；人工“接手”保留异常状态；只有之后的健康观测才能标记恢复，新的异常会重新打开。当前是一项检查一个异常记录，尚未按每个服务器实例拆分生命周期，也没有邮件/IM 通知或自动重启服务器。

这是单机、低并发调度器，不承诺大规模 SLO 或完整替代 Alertmanager。已有大规模告警、日志采集、存储和可视化继续由 Prometheus、Loki、Grafana 等组件负责，agent18 负责把证据接到支持处理流程。

## 数据、权限与代码位置

| 数据/实现 | 位置 | 边界 |
| --- | --- | --- |
| 页面上下文 | `core.case_captures`；SDK `capture.ts` / 可选 `screenshot.ts` | Case 四维 RLS；截图不进入列表，不发给分析模型 |
| 调度和异常状态 | `control.observation_jobs/schedules/incidents` | 后台路由元数据，客户没有读取接口；Owner 接口按项目限定 |
| 报告 | `core.observation_reports` | 四维 RLS；完整工程内容仅 Owner 读取 |
| 工具与策略 | `providers/observability`、`packages/application/src/gateway.ts` | 固定 `operations.observe` READ 工具；Operator 权限、注册版本、配置指纹与输出校验 |
| 持久执行 | `packages/application/src/observations.ts`、`apps/worker` | 任务、租约、重复合并、结果发布前复核 |
| 本机界面 | `apps/setup/src/observations.ts`、`apps/console/src/observations.tsx` | 继承 Owner 访问码、Host、Origin、回环地址限制 |
| 升级 | `009_operations.sql` | 追加迁移，保留已有 Case / Run / 知识 / 业务回执 |

新表与凭据文件进入现有 Core 备份。Loki、Prometheus 的独立数据卷不在 Core 数据库备份里；外部监控与 SaaS 仍需各自备份。经验草稿可从已保存报告重新生成。

## 体验与验证

按照 [真实监控接入指南](../guides/observability.md)启动可选组件，然后在演示网站点击“模拟业务异常”，通过右下角对话上报。在 Owner 的“巡检与排查”检查日志、指标、分析、异常合并与恢复。`pnpm test:observability` 自动验证真实 Loki / Prometheus 下的同一链路；页面截图需要浏览器另行验证。

自动化范围还包括 PostgreSQL / OPA 权限隔离、跨租户输出拒绝、配置与注册撤销、任务租约恢复、报告不向客户泄露、无数据不误报健康，以及原有支持/业务/备份恢复回归。具体执行记录见 [0.7 验收记录](../development/round7-operations.md)。

0.7 尚未实现完整 Trace 存储查询、服务拓扑、部署/commit 自动关联、任意 Shell/SSH/SQL、自动代码修复或 PR、远程多人客服 SSO。真实模型质量、目标 SaaS 权限和线上采集完整度必须在接入项目验证。后续扩展继续使用现有 Provider、Evidence、Policy 与业务桥合同，不应绕过这些边界。
