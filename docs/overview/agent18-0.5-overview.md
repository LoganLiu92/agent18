# agent18 0.5：运行机制与实现综述

> 历史版本/选型记录。当前能力与真实监控接入见 [0.7 运行综述](../overview/agent18-0.7-operations.md)。

agent18 把已有 SaaS 的知识、用户身份、业务接口与支持过程组织成一套可嵌入的助手。现有系统继续负责登录、业务数据库和最终业务授权；agent18 提供可配置的知识构建、客户交互、受控业务调用、问题跟进与运行工具。

本轮按“克隆 → 安装 → 接入 → 使用 → 支持 → 维护”的完整路径交付。版本为 **0.5.0 集成预览**，重点是已经接通并可验证的 L1–L3 能力。运行时根因分析和自动代码修复还没有被实现为可执行产品能力。

## 一、交付后的使用流程

部署者运行 `pnpm start`，在本机访问初始化向导。配置项目身份、模型、目录/Git 来源，生成草稿、核对引用与受众后发布，再将浮窗、内嵌区块或独立页面入口接到 SaaS。

安装完成后的默认页面是接入工作台。运行总览读真实健康与版本状态；系统与能力页面编辑身份和站点、导入 OpenAPI 查询、审核字段和角色、配置写操作桥；客户问题页面按项目收取问题并回复。知识更新与发布继续在同一套向导管理。

客户从已登录的 SaaS 打开助手，在一个持续对话中找答案、查业务、办业务和跟进问题；需要补充的信息、结果和确认都出现在消息中。独立页面具备同样功能，并保留完整目录与工作区。客户不用注册另一套账号，不向 agent18 提供密码；SaaS 的后端负责短期身份签发。具体交互与上下文边界见[对话式助手](../guides/conversation.md)。

## 二、运行组件与职责

| 组件 | 运行位置 | 责任 |
| --- | --- | --- |
| Web SDK 与助手 | 原 SaaS 页面或 Core 支持页 | 用户输入、上下文、身份获取、查询展示、操作确认 |
| Core / Fastify | 4318，公开部署通过 HTTPS 代理 | Token 校验、API、scope、OPA、知识检索、业务调用、Case/Run |
| 本地工作台 | 部署主机 127.0.0.1:4321 | 配置、资料扫描/构建、审核发布、接入管理、收件箱 |
| Worker | 独立受限容器 | 消费 pg-boss 调度，经 Core 租约执行后台支持运行 |
| PostgreSQL | 隔离数据库 | 元数据、Case/消息、Run/步骤、证据、审计、outbox、知识版本、提案 |
| OPA | 独立只读策略服务 | 默认拒绝，分阶段判断注册工具调用 |
| SaaS 身份与业务 API | 现有系统信任域 | 确认当前用户、实时业务授权、查询数据、执行和回执 |
| 可选大模型 | 接入者选择的服务 | 按资料归纳知识、基于证据回答、生成已注册动作的预览 |

Core 不拥有 SaaS 业务数据库密码。Worker 不拥有模型 Key，也不直接调用业务写入。客户不能访问工作台、配置源路径或把自己提升为部署者。

## 三、知识从代码和文档到客户答案

1. **来源配置**：目录/Git、文件范围、大小预算、内部/客户受众与允许租户。Git 固定到 commit，仅读取对象，不执行仓库。
2. **扫描与分块**：过滤依赖、产物、隐藏/凭据文件、符号链接、二进制与疑似密钥；为文件内容建立哈希与行号。Markdown 按标题和代码块边界切分，源码按受限片段处理。
3. **知识构建**：extractive 模式保存原文条目；model 模式将有限片段送给自有模型，严格校验 JSON、类别、引用 ID、正文与预算。相同片段与模型规则可复用缓存。
4. **审核发布**：来源独立构建；草稿可逐页预览文章与引用。审核通过后切换活动版本，失败保留旧快照。工作台发布会复核构建与当前受众配置；主机 CLI 的显式历史版本回滚属于部署者操作，会恢复该版本的受众，应重新审核。
5. **权限检索**：RLS 先筛选当前项目/租户可见且已发布的客户条目，再做中英文词项匹配，结合标题权重与长度归一排序，减少大段概览淹没具体操作指南。没有模型时明确显示检索，有模型时答案只能引用已检索内容。
6. **持续更新**：watch 定期读取独立项目配置，内容/修订/模型/受众/规则签名变化才重建。新版本仍是草稿；来源撤下或权限收紧会立即停止旧资料对客可见。

“所有代码”有助于理解系统，但业务规则完整性取决于源码、资料和模型输出的质量。工具会列出跳过、预算、失败和引用，不承诺只输入仓库就覆盖所有业务知识。

## 四、业务查询与代操作怎样执行

查询从 OpenAPI 3.0/3.1 JSON 导入受限 GET 候选。默认关闭，由部署者指定用户角色和可返回字段。前端只提交已注册 queryId 和业务参数；Core 先校验身份、注册、参数、OPA 和审计，再把当前用户的短期 Token 发给固定 SaaS API。后端检查对象归属，Core 做字段投影和数量限制，返回真实数据、时间和 requestId。

代操作使用三阶段桥接：

- **prepare**：后端检查对象权限和状态，返回面向用户的具体变更说明与 revision。Core 保存参数、预览、注册哈希和 5 分钟有效期。
- **execute**：用户明确确认存储的预览。Core 再查当前权限/配置/有效期，持久化 executing 和审计后发送一次；SaaS 以相同幂等键原子提交数据与回执。
- **status**：发生超时、断线或不合规响应时保留不确定状态，只读回执。没有回执不等于没有执行，不能自动再写一遍。

因此代客操作实际走**前端助手 → Core → 当前身份下的 SaaS 后端 API**。当前不使用自动点击浏览器页面。模型可以生成单步预览建议，不能临时发明接口、执行 SQL 或获得管理员身份。

示例 SaaS 用 SQLite 保存分用户订单与通知偏好。可以完整验证：查询偏好 → 预览修改 → 确认 → 得到业务回执 → 再查询实际值；同租户另一用户和另一租户均不能访问 Alice 的订单。

## 五、客户问题怎样持续处理

提交问题时，Case、首个 Run、outbox 和审计在一个 PostgreSQL 事务里保存。分发器将持久化任务投递到 pg-boss，Worker 取得受限租约后由 Core 执行当前可用的知识调查步骤，记录运行状态、证据与失败原因。

客户能查看处理进展和引用、补充说明、收到支持团队回复、确认解决或重新打开。消息按幂等键写入；客户 API 的 author 固定为 customer，本地 owner 的回复固定为 support。新的消息不会自动生成没有授权的业务动作。

后台完成资料检索不是客户已经解决；客户标为 resolved 后，晚到的后台结果不会把问题改回处理中。重新打开恢复待跟进状态，工具重试仍需显式操作。

运行支持取消、有限重试、过期预算、崩溃恢复和步骤追踪；这些主要用于可恢复的知识调查，而不是声称已实现日志根因分析或自动修复。

## 六、运维与开源交付

内置 `/docs` 提供与仓库一致的文档站点，`/openapi.json` 输出客户 API。release:check 生成 SDK、OpenAPI、MIT License 和 SHA-256 清单，便于宿主系统自托管静态资源。贡献规范、问题模板、PR 模板、许可证、版本记录和 CI 与代码一起维护。

doctor 同时用于 CLI 和工作台，检查数据库角色、FORCE RLS、迁移校验、Core、OPA、积压和配置。备份采用 PostgreSQL 一致快照、受限配置副本、SQLite 在线快照与逐文件校验清单。恢复先进入随机新库；演练会真实还原并检查基础隔离后清理临时库。切换命令只接受已验证的新库，保留原库与原配置。

默认 Compose 只绑定回环地址，演示签发器单独放在 demo profile。真实单机部署提供配置准备命令与 HTTPS 反向代理示例，只有 Core 对外发布。本地部署管理继续使用主机权限或 SSH 转发，不开放一个缺乏企业身份保护的公网管理后台。

## 八、后续演进

下一个方向是替换或新增成熟知识 provider、OIDC/JWKS 轮换适配、日志/Trace 只读连接器与编码代理隔离执行。它们应继续遵守当前的可信身份、工具注册、受众控制、分阶段执行和审计合同，而不是让模型因“拥有源码”就突破业务权限。
