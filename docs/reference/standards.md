# 技术标准与实现边界

agent18 的集成合同优先采用已有标准；扩展只覆盖自身支持工作流。这里区分“遵循某个协议子集”和“已经完整集成所有同类系统”，便于接入者评估真实工作量。

## 协议与数据标准

| 领域 | 实现 | 边界与责任 |
| --- | --- | --- |
| 身份 | JWT、EdDSA / Ed25519、公开 JWK Set、Bearer Authorization | 静态签发者和公钥；现有 OIDC/SSO 由 SaaS 会话适配为短期 Support Token |
| API 说明 | OpenAPI 3.1 客户接口；导入 3.0/3.1 受限 GET 子集 | 不自动接受任意认证、远程引用、复杂参数或写操作 |
| 浏览器接入 | ES Module、Fetch、CORS、CSP、Shadow DOM、postMessage | 精确 Origin 与窗口绑定；不读取宿主 DOM、Cookie 或网络记录 |
| 参数与配置 | TypeScript + Zod，严格字段与运行预算 | 模型输出与业务回包均视为不可信输入 |
| 授权策略 | OPA / Rego，默认拒绝，READ / PROPOSE / EXECUTE | 注册、当前身份、业务权限与最终执行分层验证 |
| 数据持久化 | PostgreSQL 17、事务、外键、唯一键、FORCE RLS | 核心组织/项目/租户/用户范围；数据库管理员本身具有管理权 |
| 后台任务 | 事务 outbox、pg-boss、租约、有限重试 | 消息可重投递，业务写操作独立走提案和回执协议 |
| 来源版本 | Git commit、文件 SHA-256、行号引用、版本发布 | 读取代码而不执行；大型/非文本内容需外部预处理 |
| 交付 | 固定依赖与基础镜像摘要、迁移校验、CI、SHA-256 发布清单 | 发布清单不是签名证明，也不是 SLSA/SBOM 认证 |

参考规范：[OpenAPI 3.1.1](https://spec.openapis.org/oas/v3.1.1.html)、[OAuth Bearer Token Usage / RFC 6750](https://www.rfc-editor.org/rfc/rfc6750)、[JWT / RFC 7519](https://www.rfc-editor.org/rfc/rfc7519)、[JWK / RFC 7517](https://www.rfc-editor.org/rfc/rfc7517)。这些是互操作依据，不代表 agent18 是通用 OAuth 授权服务器。

## 身份和权限的责任链

SaaS 负责确认用户登录、租户成员关系、角色及业务对象权限。Core 验证签名和项目绑定，从可信身份建立数据库 scope。OPA 决定该阶段是否允许调用某类已注册工具。业务系统收到用户身份后再做当前权限、对象归属与数据版本验证。

模型可以理解资料、提出动作，但不能创建角色、工具、URL、SQL 或执行权限。代码仓库中的文字不是系统指令；文章和上游响应不会成为新的工具注册。

本地部署者使用单独的访问码和主机权限，能够维护配置、构建知识并回复客户。这个角色没有伪装成客户的公开入口；客户声明 `roles: [admin]` 也不会获得本地 owner 权限。

## 持久化与失败语义

Case 创建、首个 Run、outbox 和审计同一事务提交。Worker 接收调度 ID，经 Core 获取受限租约，Core 再按持久化 scope、预算、取消状态和当前策略执行。步骤、证据与审计只追加，普通应用角色不能篡改历史。它们不宣称可抵御数据库管理员改写的密码学防篡改。

业务写入使用另一条路径：存储提案 → 当前用户确认 → 提交执行前审计 → 单次派发 → 保存业务回执。超时可能意味着后端已经提交，因此保持 uncertain 并只读回执。不能用自动重发写入来恢复“看起来失败”的请求；正确性依赖 SaaS 的幂等键和业务数据/回执同事务。

知识构建产生不可直接对客的新版本；发布是独立动作。扫描、模型或资料引用校验失败不会取代已发布版本。受众收紧和来源撤下会让历史 Case 中相应证据也不可见。

客户 resolved 与自动调查完成是不同事件。客户可补充、解决、重开；工作人员回复以明确 author 记录。重开不自动产生新一轮工具调用，Run 的显式重试保留原次数和预算边界。

## 当前可交付范围

| 层级 | 0.6 实现情况 |
| --- | --- |
| L1 产品知识与客服 | 文档/代码索引、模型整理、审核发布、引用问答、客户问题与人工回复 |
| L2 用户与页面上下文 | 短期身份、项目/租户/用户 scope、显式页面和业务对象上下文 |
| L3 业务能力 | OpenAPI GET 导入、字段投影、用户身份查询、显式确认的单步办理 |
| L4 运行调查 | 通用 Evidence/RunStep、注册中心与策略已落地，合成日志适配器通过完整执行测试；尚未连接 SaaS 日志、指标、Trace 或数据库调查工具 |
| L5 代码修复 | 尚未接入编码代理、沙箱、修复分支或 PR；不会在部署机器上执行客户仓库 |

当前检索是可解释的词项匹配与可替换 provider 边界，不是成熟向量数据库的全面替代。PDF/OCR、外部知识服务、MCP、GraphQL、W3C Trace Context/OTel、远程 JWKS 轮换、企业管理 SSO、跨实例全局限流、自动多步任务与 HA 均未宣称完成。继续扩展应使用适配器接入成熟组件，保持当前身份和审批边界。

## 质量与兼容性要求

每次新增业务能力都要验证允许路径、拒绝路径、投递不确定性和实际数据，而不是只检查 HTTP 200。每次新增数据库表都需要 scope、外键、权限和反向隔离测试。所有日志与客户错误不得包含凭据或上游原始错误正文。

最低验证包括类型检查、构建、单元测试、OPA、数据库集成、任务恢复、隔离的安装旅程和真实浏览器体验。模型测试可使用协议模拟服务验证错误与响应合同；只有使用接入者实际 Key 和模型跑过的请求，才是该供应商的真实兼容性证据。

## 0.6 核心合同

参见 [Core Foundation](../overview/agent18-0.6-core.md) 与 [注册规范](providers.md)。Policy 使用 Principal / Action / Resource / Context 和 ALLOW、DENY、APPROVAL_REQUIRED；Case 的 Evidence 从 Citation 升级为独立 envelope。前端环境标签不进入可信授权条件，通用 Run 只允许读操作，MCP 作为 transport 预留而不是领域 Provider。
